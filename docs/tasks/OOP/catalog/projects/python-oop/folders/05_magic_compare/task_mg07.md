# Задача MG07: Очередь заявок теряет порядок

## Условие

### Как это работает

Метод `__lt__` отвечает на вопрос «должен ли `self` стоять раньше `other`?». Когда главное поле у двух объектов равно, решает **второе** поле. Если второй `return` снова сравнивает главное поле, то при равенстве ответ всегда `False`, а `sorted` оставляет такие объекты в исходном порядке:

```python
def __lt__(self, other):
    if self.score != other.score:
        return self.score > other.score
    return self.score < other.score          # снова score: при равных очках всегда False
```

| Очки | Что вернёт `__lt__` |
|---|---|
| разные | верно: больше очков идёт раньше |
| равные | всегда `False`: второго критерия нет |

Исправление: во втором `return` сравнить другое поле (то, что должно решать при равенстве главного).

### Задание

Заявки службы поддержки сортируются так: сначала больший `priority`, а при равном приоритете раньше идёт заявка с **меньшим** `number`. Сейчас второй критерий не работает, и заявки с равным приоритетом остаются в том порядке, в каком пришли. Найди ошибку в `__lt__` и исправь.

## Аргументы

- `rows` — список пар `[номер, приоритет]`, оба целые (список может быть пустым).

## Возвращает

Список номеров заявок в порядке `sorted`: приоритет по убыванию, при равенстве номер по возрастанию.

## Правила

- Исправь только метод `__lt__`; `__init__` и рамку не трогай.
- Метод должен возвращать `True` или `False`.

## Пример

```python
task_mg07_queue([[2, 2], [1, 2], [3, 1]])   # -> [1, 2, 3]
task_mg07_queue([[1, 1], [2, 3], [3, 2]])   # -> [2, 3, 1]
```

## Учебные цели

- Находить в `__lt__` неверное поле во втором критерии.
- Проверять порядок на данных с равным главным значением.

## Проверка понимания

Почему в исходной версии заявки с равным приоритетом остаются в порядке прихода? Как поменять `__lt__`, чтобы при равенстве раньше шла заявка с большим номером?
