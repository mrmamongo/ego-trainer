# Задача ER15: Режим preview

## Условие

### Как это работает

Перед тем как менять состояние, иногда полезно **показать**, что произойдёт: «если применить это действие, золота станет столько-то». Это режим **preview** (предпросмотр). Он должен считать то же самое, что обычный режим, но не менять состояние.

Сейчас функция `task_er15_apply_action(state, action)` из файла задачи умеет только применять действие. Самая надёжная правка — не переписывать её, а **вынести старое поведение в помощника** (последняя строка таблицы из урока `fd-modify`) и обернуть:

```python
def apply_now(state, action):                       # старый код без изменений
    ...

def task_er15_apply_action(state, action, preview=False):
    answer = apply_now(state, action)               # считаем как раньше
    ...                                             # и решаем, что вернуть
```

Новый параметр `preview` имеет значение по умолчанию `False`: старые вызовы с двумя аргументами не ломаются.

Новый ответ получает пятое поле `preview_state` (предсказанное состояние). Что вернуть в каждом случае:

| Режим | Результат действия | `status` | `state` | `result` | `reason` | `preview_state` |
|---|---|---|---|---|---|---|
| обычный | успех | `"done"` | новое | как раньше | `None` | `None` |
| обычный | отказ | `"rejected"` | исходное | `None` | код | `None` |
| `preview=True` | успех | **`"preview"`** | **исходное** | предсказанный | `None` | **новое** |
| `preview=True` | отказ | `"rejected"` | исходное | `None` | код | `None` |

Отказ в режиме preview выглядит так же, как обычный отказ: предсказывать нечего.

### Задание

Раньше функция только применяла действие и возвращала четыре поля. Теперь она принимает необязательный параметр `preview` (по умолчанию `False`) и всегда возвращает пять полей, включая `preview_state`. Правила покупки и сброса предмета остались прежними: `buy` проверяет `bad_price`, `already_owned`, `not_enough_gold`, `drop` проверяет `not_owned`, иначе `unknown_tool`. Измени готовую функцию, не пиши её с нуля.

### Что дальше

Тот же приём предпросмотра применяется в продуктовой задаче [XL-A15](task:XL-A15), там для событий гильдии. Идею «обёртка вокруг старого поведения» ты увидишь и в других задачах.

## Аргументы

- `state` — словарь `{"gold": целое число, "items": список строк}`.
- `action` — словарь `buy` (с `item` и `price`) или `drop` (с `item`).
- `preview` — необязательный, по умолчанию `False`.

## Возвращает

Словарь `{"status", "state", "result", "reason", "preview_state"}` как в таблице выше.

## Правила

- Измени готовый код: не переписывай логику `buy` и `drop`, а добавь параметр и пятое поле.
- Вызов с двумя аргументами должен вести себя как раньше (плюс поле `preview_state` со значением `None`).
- Входные `state` и `action` не меняй, в том числе в режиме preview.
- Функция должна **вернуть** значение через `return`, а не печатать его.

## Пример

```python
state = {"gold": 100, "items": []}
action = {"tool": "buy", "item": "щит", "price": 30}
task_er15_apply_action(state, action, True)
# -> {"status": "preview", "state": {"gold": 100, "items": []}, "result": {"item": "щит"},
#     "reason": None, "preview_state": {"gold": 70, "items": ["щит"]}}
```

## Учебные цели

- Добавить режим к готовой функции, не сломав старый.
- Отделять «посчитать» от «применить».

## Проверка понимания

Какое состояние возвращается в поле `state` в режиме preview и почему не новое? Что получится при preview, если покупка невозможна?
