# Отказ как значение: {status, reason} или исключение

Есть два способа сообщить, что действие не удалось:

| Способ | Как выглядит | Кто узнаёт |
|---|---|---|
| исключение | `raise BudgetError("…")` | тот, кто вызвал, и только если он поймает |
| значение | `{"status": "rejected", "reason": "budget"}` | любой, кто прочитает ответ |

## Правило выбора

- **Внутри кода**, между своими функциями, удобны исключения: они прерывают лишнюю работу и не дают забыть про ошибку.
- **На границе модуля**, там, где ответ уходит пользователю, интерфейсу или другому сервису, нужно **значение**: понятный словарь, который можно показать, записать в журнал или сравнить в тесте.

Типичная схема: внутри `raise`, а на границе одна функция ловит и переводит ошибку в словарь.

```python
def apply_action(state, action):
    try:
        new_state = do_it(state, action)         # внутри могут быть raise
    except BudgetError:
        return {"status": "rejected", "state": state, "result": None, "reason": "budget"}
    return {"status": "done", "state": new_state, "result": None, "reason": None}
```

## Формат ответа

В продуктовых задачах помощника гильдии ответ всегда одной формы:

```python
{"status": "done" или "rejected", "state": ..., "result": ..., "reason": ...}
```

| Поле | При успехе | При отказе |
|---|---|---|
| `status` | `"done"` | `"rejected"` |
| `state` | новое состояние | **исходное** состояние, не изменённое |
| `result` | что получилось | `None` |
| `reason` | `None` | код отказа: `"budget"`, `"unknown_item"` … |

Код отказа — короткая строка из договорённого списка, а не фраза: по нему можно писать `if`, и он не зависит от языка.

## «Ложный успех»

Самый опасный баг — когда действие **отклонено**, а ответ говорит `"done"`. Обычно так получается, когда `status` выставили заранее и забыли поменять в ветке отказа:

```python
answer = {"status": "done", "state": new_state, "reason": None}
if not ok:
    answer["reason"] = "budget"     # status всё ещё "done"!
return answer
```

Пользователь видит «готово», хотя ничего не произошло. Чини так: при отказе возвращай **целиком другой** словарь, а не правь поля готового.

## Отказ не должен портить состояние

При отказе в `state` должно остаться то, что пришло на вход. Нельзя сначала изменить данные, а потом обнаружить ошибку: сначала **проверки**, потом изменения. Если нужны изменения заранее, делай их в копии.

## Проверь себя

```python
def take(stock, item):
    if item not in stock:
        return {"status": "rejected", "reason": "unknown_item"}
    stock.remove(item)
    return {"status": "done", "reason": None}
```

1. Что вернёт `take(["меч"], "щит")`, и изменится ли список?
2. Что станет со списком после `take(["меч"], "меч")`?

<details><summary>Ответ</summary>

1. `{"status": "rejected", "reason": "unknown_item"}`; список остался прежним: проверка идёт до изменения.
2. Список станет пустым — функция изменяет аргумент. Для задач с «исходным состоянием» это уже плохо: вернуть надо новый список, а входной не трогать.

</details>
