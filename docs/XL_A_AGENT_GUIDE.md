# Руководство агента: задачи Cogito

Это рабочий порядок для задач XL-A и следующих каталогов в `ego-trainer`.
Перед авторингом прочитай корневой `AGENTS.md`, этот файл и относящиеся к
задаче разделы `docs/TASK_AUTHORING.md` и `docs/TESTS_DESIGN.md`.

## 1. Сначала выбери область изменения

| Запрос | Где править |
| --- | --- |
| Исправить или уточнить XL-A01…XL-A27 | Исходный `student.py` в одной из девяти папок `docs/tasks/XL-A/`; затем пересобрать каталог |
| Добавить задачу после XL-A27 | Создать отдельный проект/пачку по `docs/TASK_AUTHORING.md` (например, `docs/tasks/XL-B/catalog/`) |
| Продолжить XL-A новыми ID по прямому запросу | Сначала расширить генератор и его проверки: текущий генератор намеренно принимает ровно XL-A01…XL-A27 |

Каталог `docs/tasks/XL-A/catalog/` для XL-A генерируется скриптом.
Не вноси туда вручную новые `.md`, `.student.py` или YAML: `--check` не
считает их источниками истины и не защитит такую правку при следующей
генерации. Файлы `.solution.py` и `.tests.py` генератор не создаёт и не
перезаписывает; это авторские файлы рядом с сгенерированной задачей.

Новая задача XL-A требует согласованно изменить источники и проверки:

- разбиение ID по группам и функции `task_xlaNN_*` в исходниках;
- `GROUPS`, извлечение условий и метаданных в `scripts/build_xl_a_catalog.py`;
- карту общих договоров и преобразований условий, если они нужны;
- проверку диапазона ID, состава каталога, папок и распределения типов;
- `scripts/verify_xl_a_catalog.py`, имя и размер пачки в README;
- проверку версий, чтобы изменение одного выпущенного задания не сбрасывало версии остальных.

До такой работы каталог не принимает XL-A28. Если запрос явно разрешает
продолжить XL-A, включи эти изменения в объём и проведи полный прогон.

## 2. Зафиксируй договор задачи в исходном `student.py`

В XL-A авторский источник — один из файлов:

```text
docs/tasks/XL-A/01_chat_context/student.py
docs/tasks/XL-A/02_quest_journal/student.py
docs/tasks/XL-A/03_party_finder/student.py
docs/tasks/XL-A/04_answer_sources/student.py
docs/tasks/XL-A/05_guild_assistant/student.py
docs/tasks/XL-A/06_crafting/student.py
docs/tasks/XL-A/07_market/student.py
docs/tasks/XL-A/08_assistant_memory/student.py
docs/tasks/XL-A/09_agent_plans/student.py
```

Сохраняй найденные в группе общие форматы данных и helper-функции `GIVEN`.
Условие одной задачи должно содержать всё необходимое для решения: точную
сигнатуру и типы входов, структуру результата, порядок проверок и ошибок,
правила копирования/мутации, примеры и ожидаемые значения. Ученик не должен
искать требуемый формат в другой задаче.

Для новых пачек держи домены продуктовыми: LLM, agents, игры и MMO. Смешивай
по запросу задачи на поиск багов, правки и новый код; не превращай пачку в
инфраструктурный курс без прямого указания.

Первой строкой docstring функции XL-A служит заголовок генератора:

```text
XL-A28. НАЙТИ БАГ — короткое название
```

Для текущей пачки используй типы `НАЙТИ БАГ`, `ПРАВКИ` или `НОВЫЙ КОД`.
Оставляй намеренный баг в теле задачи на поиск ошибки, рабочее исходное
поведение — в задаче на правки, а `pass` — в задаче на новый код. Нужные
функции, импорты и `GIVEN` должны попадать в сгенерированный starter по
зависимостям самой функции; не связывай starter с `task_*` другой задачи.

Условия для новых задач должны быть автономными. В исходнике можно
переиспользовать `GIVEN`, но ученик не должен зависеть от запуска другой
задачи или знать её внутреннее решение.

## 3. Сгенерируй только файлы, принадлежащие генератору

Из корня репозитория:

```console
uv run python scripts/build_xl_a_catalog.py
uv run python scripts/build_xl_a_catalog.py --check
```

В нынешнем генераторе его 66 файлов — это catalog/project/folder YAML,
условия `.md`, стартеры `.student.py` и README. Он сохраняет вручную
написанные `.solution.py` и `.tests.py`.

После регенерации проверь diff исходного `student.py` и каталога. Убедись,
что starter сохранил намеренный баг или `pass`, все необходимые `GIVEN`,
сигнатуру и достаточно полный docstring. Проверь отсутствие зависимости от
других задач и несогласованных ссылок на номера XL-A.

## 4. Напиши эталон и тесты отдельно

Для каждой новой задачи создай рядом четыре файла с одним префиксом:

```text
task_xlaNN.md                 # генерируется из student.py
task_xlaNN.student.py         # генерируется из student.py
task_xlaNN.solution.py        # авторский эталон
task_xlaNN.tests.py           # авторские проверки
```

У нового проекта без генератора `.student.py` можно оставить необязательным,
если безопасно сгенерированный starter точно соответствует заданию. Добавь
sidecar, когда важно сохранить намеренный баг, `pass` или готовый `GIVEN`.

Имя функции и её сигнатура в starter и эталоне должны совпадать. Эталон
должен реализовывать текстовый договор, а не компенсировать его неописанные
случаи. В `@case` задавай независимые входы и конкретные ожидаемые значения;
не вычисляй ожидание вызовом эталона или решения ученика.

В тестах XL-A:

- используй `comparison="value"`, если результат — вложенные структуры,
  для которых порядок ключей словаря не является частью договора. Типы
  значений и порядок последовательностей при этом всё ещё важны;
- ставь `check_inputs_unchanged=True`, если задача запрещает менять входы;
- добавляй `check_result_isolated=True`, когда требуется вернуть независимую
  структуру, и проверь это негативным примером поверхностной копии;
- используй `input_aliases` только если условие требует сохранить общие
  вложенные объекты входа. Формат флагов смотри в начале `docs/TESTS_DESIGN.md`;
- оставляй не меньше трёх smoke-кейсов и добавляй full-кейсы для границ и
  приоритетов ошибок. Полный верификатор ожидает оба уровня.

Ожидания держи понятными и конечными: важное правило должно иметь кейс,
который отличает корректное решение от правдоподобного ошибочного.
Делегируя работу, назначай агентам непересекающиеся ID и явный список файлов;
сохраняй за интегрирующим агентом общие контракты, генератор, версии и
финальную сверку всех результатов.

## 5. Проведи полную проверку XL-A

Из корня репозитория:

```console
uv run python scripts/build_xl_a_catalog.py --check
uv run python -m scripts.verify_xl_a_catalog --timeout 10
uv run pytest tests/test_parser.py tests/test_checker.py tests/test_runner.py tests/test_testing.py tests/test_content_repo.py tests/test_catalog.py tests/test_server_sync.py tests/test_server_tasks.py
```

Верификатор прогоняет все эталоны с уровнями `all`, а стартеры — со
`smoke`. Он проверяет 27 ID, девять папок, одинаковые сигнатуры, девять
задач каждого типа и то, что заготовки ещё не решены. XL-A25 — исключение:
это задача на структурный рефакторинг с прежним поведением, поэтому тесты
принимают исходный starter. Разбиение на helpers проверяется отдельно при
ревью.

Если добавляется другой проект, скрипт `verify_xl_a_catalog.py` его не
проверяет. Добавь для него такую же проверку через parser и checker и обнови
тесты каталога/синхронизации согласно `docs/TASK_AUTHORING.md`.

При неожиданном падении раздели дефект задачи и нестабильный запуск sandbox:
посмотри конкретный кейс/ошибку, повтори только этот случай и не объявляй
непроверенную задачу готовой.

## 6. Соблюдай версии и границу публикации

Каталог XL-A использует `version_policy: declare`. Новый уникальный ID
начинается с `1.0.0`. При изменении уже выпущенного ID контент с тем же
хешем пропускается; изменённое содержимое требует большей SemVer-версии,
иначе sync отклонит эту задачу. Сейчас XL-A-генератор подставляет одну
константу `VERSION = "1.0.0"` для всех задач. Поэтому перед изменением
выпущенного задания сначала добавь в генератор отдельные версии по ID и
покрой проверкой, что версия поднята только у изменённой задачи. Не меняй
глобальную константу ради одного задания: это затронет весь каталог.

Хеш задачи в текущем parser включает условие, starter и solution, но не
`.tests.py`. Поэтому изменение только тестового sidecar тоже должно
поднимать версию задачи. Это правило описано в §4 `docs/TASK_AUTHORING.md`.

`docs/tasks/` — исходники/fixture репозитория. Сервер читает свой настроенный
content-repo или локальный mount. Команда `sync-tasks --from ...` запускается
в БД, заданной серверной конфигурацией: не направляй её на production и не
переноси туда файлы без прямого запроса на публикацию. Production-релиз
требует отдельного явного запроса; затем следуй `docs/DEPLOYMENT.md`,
ADR-0016 и инструкции резервного копирования/релиза. Успешная локальная
генерация сама по себе не означает, что контент опубликован.
